# LexDraft — Engine API Layer: Design Plan

Status: **proposal, no code written.** Decides the contract between the Python
drafting engine (`lexdraft-engine/`) and the TypeScript API/frontend (`LexDraft/`).

Two decisions are already made and are treated as fixed here:

1. **FastAPI service wrapping the engine** — not a subprocess. Refusals are
   structured objects with computations attached; they need a real wire contract,
   not stdout parsing.
2. **Route the whole document** — not just the framework decision. Partial routing
   would leave the s.141 hard refusal, the limitation checks, the injunction triad,
   the VERIFY markers and the sign-off banner all bypassed while *looking*
   connected — worse than no routing.

---

## 0. The problem this fixes (one paragraph)

Today the Draft page generates from a model. The TS orchestrator runs
EXTRACT → CLASSIFY → DRAFT → VERIFY against Anthropic/xAI; **nothing calls the
engine.** The BNS/BNSS section decision is the model's (the CLASSIFY prompt), and
the only deterministic TS piece — `old-to-new-law.ts` — is a hand-maintained flat
map with no date/provenance logic, doing a *different* job than the engine's
`dual_code_router`. So the engine's router, refusals, VERIFY registries, sign-off
and templates are all dark, and the model re-decides, less rigorously, things the
engine already decides deterministically. The API layer connects them.

---

## 1. What each side owns after the change

| Concern | Owner |
|---|---|
| Which BNS/BNSS/CrPC sections a doc cites | **Engine** (`dual_code_router` + `section_mappings` VERIFY table) |
| Whether a document may be generated at all (refusals) | **Engine** (pipeline `build()` + rules) |
| The document structure / templates | **Engine** (`templates/shared/*.docx`) |
| VERIFY table markers + review banner + sign-off | **Engine** (`src/verify/*`) |
| Free-text brief → fact-sheet fields | **Model** (extraction) |
| Follow-up questions when fields are missing | **Model** (clarify), *informed by the engine's required-fields + refusal* |
| Narrative-slot prose (`[to be drafted]`) | **Model** (drafting) |
| Everything else in drafting | **Nobody new** — see §7 for TS capabilities with no engine equivalent |

The model's job shrinks to three things: **extract, clarify, draft slots.**
Nothing else. It never decides sections, never states a refusal, never fills a
figure that comes from a VERIFY table.

---

## 2. Service shape

A FastAPI app in a new `lexdraft-engine/service/` package, deployed alongside the
engine (same repo, same venv). It imports the engine directly — no duplication.

```
POST /v1/route-code           # dual_code_router only (cheap, used by clarify)
POST /v1/draft/{doc_type}     # the whole document: build() -> refuse | render
POST /v1/sign-off             # mark a rendered document final (audit trail)
GET  /v1/doc-types            # machine-readable field/slot contract per pipeline
GET  /v1/verify/tables        # Section A data (already generated by the engine)
GET  /v1/verify/averments     # Section B data
GET  /v1/refusals             # Section C data (generated refusal catalogue)
GET  /healthz
```

The Node API calls this service over HTTP (internal network, service-to-service
auth via a shared token in `env`; never exposed to the browser directly — the Node
API stays the only public surface, so tenancy/quota/rate-limiting still gate every
call).

### Why FastAPI specifically
- Pydantic models give us the request/response contract *as code*, and generate an
  OpenAPI schema the TS side can codegen types from (kills contract drift).
- Async so a slow render doesn't block the worker.
- The engine is synchronous CPU work; run `build()`/render in a threadpool
  (`run_in_threadpool`) so the event loop stays free.

---

## 3. The request/response contract, per pipeline

### 3.1 The shape of the problem

Each engine `build()` takes a **different, strongly-typed kwarg set** (plaint wants
`forum`/`territorial_bases`/`principal`/…; s.138 notice wants `cheques`/
`memo_received_date`/…). We do **not** want 16 bespoke endpoints with 16 hand-kept
request schemas drifting from the Python signatures. Two layers solve this:

1. **`GET /v1/doc-types`** returns, per pipeline, the machine-readable field
   contract: each field's key, type, required?, and enum options; plus the list of
   narrative slots. This is generated by introspecting each pipeline's `build()`
   signature + a small per-pipeline metadata block the engine already half-has (the
   averment registry names the doc; the pipeline module names the template). The TS
   side renders forms and validates from this — the schema has ONE source (Python).

2. **`POST /v1/draft/{doc_type}`** takes a single generic envelope:

```jsonc
// request
{
  "matter": {                      // the versioned fact-sheet identity (see §5)
    "matter_id": "…",              // from the fact sheet, not invented
    "version": 3
  },
  "fields": { … },                 // doc-specific, validated against /doc-types
  "slots":  { "facts": "…", "grounds": "…" },   // model-drafted narrative
  "render": true                   // true -> also return a .docx; false -> dry-run
}
```

`fields` is a flat JSON object; the service maps it to the pipeline's kwargs via a
per-pipeline adapter (the one place doc-specific knowledge lives, in Python, tested
against the pipeline). Dates arrive as ISO strings and are parsed to `date`; enums
arrive as their `.value` strings and are mapped back to the enum. A field that
fails to map is a **422 validation error** (not a refusal — see §4: a malformed
request and a legal refusal are different animals).

### 3.2 The success response

```jsonc
{
  "outcome": "generated",
  "doc_type": "plaint",
  "signals": {
    "review_banner": "[DRAFT — for advocate review; …]",   // "" if signed off
    "unverified_marker": "[figures unverified — …]",        // "" if tables verified
    "unverified_tables": ["court_fee_ad_valorem_slabs", "pecuniary_limits"]
  },
  "computations": {            // the engine's shown maths, for display
    "court_fee": 66490,
    "valuation_basis": "ad valorem on the sum of Rs. 802400/- claimed",
    "code_framework": "bnss",
    "cited_sections": { "regular_bail": "Section 483 BNSS" }
  },
  "unfilled_slots": ["grounds"],       // slots still [to be drafted]
  "docx_base64": "…"                    // present iff render:true
}
```

The `computations` block is the deterministic output the frontend renders as
facts — the fee, the resolved framework, the cited section. **These come from the
engine, so the model never states them.** `signals` drives the two banners the UI
already knows how to show.

### 3.3 The dry-run (`render: false`)

Returns everything except `docx_base64`. This is what the **clarify loop** calls:
it runs `build()` to see whether the document *would* generate, and if it refuses,
gets the structured refusal back (below) to turn into a follow-up question — all
before spending a render or showing the advocate a document.

## 4. How a refusal serialises — the important one

A refusal is **not an error**. It is a legal finding: "this document may not be
generated, here is why, here is the computation behind it." It must never surface
as a 500, and it must carry enough structure for the frontend to render it as a
*conversational message* ("I can't draft this yet — the cheque was presented after
its validity expired; here are the dates") rather than a stack trace.

### 4.1 HTTP status
`POST /v1/draft/{doc_type}` returns **HTTP 200** for a refusal. The refusal is a
*valid, successful* answer to "can this be drafted?" — the answer is "no, and
here's the legally-reasoned why." Reserving non-2xx for transport/validation
failures keeps the frontend's error handling clean: 4xx/5xx = something broke;
200 with `outcome:"refused"` = the engine has a finding to show.

### 4.2 The refusal body

```jsonc
{
  "outcome": "refused",
  "doc_type": "s138_notice",
  "refusal": {
    "code": "cheque_presented_after_validity",   // stable, machine-routable
    "reason": "cheque 452118 presented beyond validity: presented 2024-11-08, cheque dated 2024-05-04, valid to 2024-08-04",
    "computation": "cheque 452118: valid_to=2024-08-04, presented=2024-11-08",
    "pipeline": "s138_notice",
    "spec": "2.2",
    "severity": "hard",          // hard = no document; see §4.4 for the soft kind
    "fields_implicated": ["cheques[0].date", "presentation_date"],
    "remedy_hint": "auto_attach_none"   // or e.g. "auto_attach_condonation"
  }
}
```

Field-by-field:

- **`code`** — a stable slug the frontend can branch on and localise, independent
  of the human wording. *This does not exist in the engine yet* (most refusals are
  bare `reason` strings). Adding a code to every refusal is a prerequisite work
  item (§8, step 1) — it's also what makes the refusal catalogue (`/v1/refusals`,
  the existing generated Section C) a typed contract rather than prose.
- **`reason`** — the exact advocate-facing sentence the engine already produces.
  Rendered verbatim in the conversational message.
- **`computation`** — the shown maths (dates, day counts, amounts). The engine
  already attaches this to the high-stakes refusals (s.138 windows, default-bail
  sequence, pecuniary limits). Rendered as the "here's the arithmetic" detail line.
- **`fields_implicated`** — which request fields the refusal turns on, so the UI
  can highlight them in the form / focus the clarify question. Derived from the
  pipeline adapter (it knows which kwarg produced the stop).
- **`remedy_hint`** — some "refusals" in the engine are *not* refusals: the s.138
  complaint out-of-window case auto-attaches a s.142(b) condonation and still
  generates; consumer 2-yr lapse auto-attaches condonation; contested-divorce
  within a year auto-attaches s.14 leave. Those return `outcome:"generated"` with a
  `remedy` note, NOT a refusal. `remedy_hint` on a true refusal tells the UI
  whether a remedy path exists.

### 4.3 Why a typed `code`, not just the string

The frontend needs to do three different things with three different refusals:
- `no_territorial_jurisdiction` → ask the advocate *where* the cause of action arose
  (a clarify question, re-run on answer);
- `s141_company_accused_averment_missing` → explain this is a hard bar and offer to
  add the averment;
- `default_bail_extinguished` → explain the right is gone and suggest regular bail.

Branching on a stable `code` is robust; branching on `reason.includes("territorial")`
is not. The code is the contract; the reason is the display text.

### 4.4 Two severities

- **`hard`** — no document is produced (`s.141` missing, time-barred suit,
  triad limb missing). `outcome:"refused"`, no `docx_base64`.
- The **auto-attach** cases are not refusals at all — they generate WITH an extra
  application and a `remedy` note. Kept out of the refusal channel entirely so the
  frontend never mistakes "generated with a condonation attached" for "blocked."

### 4.5 Transport/validation failures (the real errors)

- **422** — request didn't match the doc-type field contract (missing required
  field, unparseable date, unknown enum). Body: `{ "error": "validation", "issues": [...] }`.
  This is a *client bug or an incomplete form*, distinct from a legal refusal.
- **404** — unknown `doc_type`.
- **5xx** — the engine raised an unexpected exception (a real bug). Logged; generic
  message to the client. Note the engine deliberately raises `*InputError` for
  a few impossible-input cases (negative amounts etc.); the service catches those
  at the adapter and converts to **422**, never a 500, because they mean "the form
  let through a value it shouldn't have."

## 5. Where the model still belongs (and only here)

Three jobs, each with a clean handoff to the engine:

### 5.1 Extraction: free-text brief → fact-sheet fields
The advocate types/dictates a brief. The model extracts structured field values for
the target doc type. **The doc type's field contract comes from `/v1/doc-types`**,
so the model extracts into exactly the shape the engine's `build()` expects — no
guessing at field names. Output: a partial `fields` object + a list of fields it
couldn't fill.

This is the existing TS EXTRACT stage, re-pointed: today it extracts into an
ad-hoc shape; tomorrow it extracts into the engine's contract.

### 5.2 Clarify: follow-up questions when fields are missing
Two sources of "what's missing," combined:
- **Required-but-absent** fields from `/v1/doc-types` (structural).
- **Refusal-driven** questions: call `/v1/draft` with `render:false`; if it refuses
  with, say, `no_territorial_jurisdiction` and `fields_implicated:["territorial_bases"]`,
  the model asks *that* question specifically. The engine tells the UI what's
  legally missing; the model phrases the question conversationally.

This is strictly better than today: the model currently guesses what to ask; the
engine now tells it, grounded in the actual refusal.

### 5.3 Narrative slots: the `[to be drafted]` prose
The engine renders everything except the narrative paragraphs (facts, grounds,
prayer prose), which come back as `unfilled_slots`. The model writes those, and
they're passed back in `slots` on a second `/v1/draft` call to render the final
document. **The model writes prose into a fixed structure it cannot alter** — it
can't move a section, can't change a citation, can't fill a figure.

Crucially: a document with a still-unfilled slot **cannot be signed off** (the
engine's existing rule), so the model's failure to fill a slot can never produce a
"final" document.

### 5.4 What the model must NOT do
Not decide sections. Not state the court framework. Not compute the fee or the
compensation. Not assert a limitation outcome. Not author a refusal. Every one of
those is now an engine call whose result the model may *quote* but not *originate*.

## 6. Fact-sheet identity is the spine

`matter_id` and `version` come from the versioned `MatterFactSheet`, never the
caller (this is already true inside the engine's sign-off). The API carries them in
the `matter` envelope on every `/v1/draft` and `/v1/sign-off` call. Consequences:

- **Sign-off** records `(document, matter_id, version, reviewer, signed_on)` in the
  engine's audit trail. `/v1/sign-off` is a thin pass-through to `signoff.sign_off`.
- **Stale sign-off** — if the advocate revises the facts (new fact-sheet version)
  after signing, the next render's `review_banner` comes back non-empty again
  (engine logic, already built). The frontend shows the draft banner without any
  extra work.
- The Node side must map its own case/matter record to a `MatterFactSheet`. Today
  the TS `resolveCaseFacts` pulls court/CNR/FIR/parties from the case record — that
  is the raw material for constructing the fact sheet. **This is a real build item**
  (§8): the fact-sheet is the engine's input-of-record and the TS case-record must
  feed it.

## 7. TS capabilities with NO engine equivalent — flag before routing around them

These are the things the current TS pipeline does that the engine does **not**.
Each needs an explicit decision: keep in TS (in front of the engine), port to the
engine, or drop. **None should be silently lost by routing.**

1. **Offence-KB retrieval + `verification` gate** (`offence-kb.service`,
   `procedure-kb.json`). CLASSIFY picks BNS *offence* sections from a curated
   knowledge base, and each carries a `verified`/`suggested` status that hedges the
   citation. The engine's `dual_code_router` resolves *procedural* framework
   sections (bail/maintenance/etc.), **not substantive offence sections** — it does
   not know that "cheating" is BNS 318. **These are complementary, not redundant.**
   → **Keep the offence-KB in TS as a retrieval step feeding `fields`**, OR port it
   into the engine as a new VERIFY-backed table. My recommendation: keep it in TS
   for now (it's real, curated, and orthogonal to the router); revisit porting once
   routing is proven. This is the one place I'd *not* delete TS logic.

2. **The VERIFY audit stage** (`buildVerifyStage`) — re-reads the *drafted prose*
   for hallucinated citations, unsupported facts, leftover placeholders, and
   repealed-law references, and hard-blocks export. The engine has nothing that
   audits model prose (it assumes the slots are trusted input). Since the model
   still writes the narrative slots, **this audit is still needed** — on the slot
   text, before it's passed back to `/v1/draft` for the final render.
   → **Keep VERIFY in TS**, narrowed to auditing slot prose (its citation-allow-list
   now comes from the engine's `cited_sections`, not CLASSIFY).

3. **TRIAGE / docType detection** (`draft-triage.service`) — one free-text input →
   which document to draft. The engine has no "figure out what they want" step; it
   assumes you already chose the pipeline. → **Keep in TS.** It selects which
   `/v1/draft/{doc_type}` to call.

4. **Quota, usage metering, tenancy, rate-limiting** (`ai-quota`, `ai-usage`,
   `firmIdForUser`, `llmGenerationLimiter`). Engine has none — it's single-tenant
   library code. → **Stays in the Node API**, which remains the only public surface
   and gates every engine call.

5. **Streaming (SSE)** — `/generate/stream`, `/agent/stream` stream tokens to the
   editor. The engine render is a single synchronous artifact, not a token stream.
   → **The narrative-slot drafting can still stream** (it's a model call); the
   engine render is a discrete final step after slots are done. The UX becomes:
   stream the slot prose, then "assembling document…" then the rendered docx.

6. **Case-record + case-notes context** (`resolveCaseFacts`, `resolveNotesForDraft`)
   — folds the firm's case record and shared notes into the model's context. Engine
   takes only explicit fields. → **Stays in TS**, feeding extraction (§5.1) and the
   fact-sheet construction (§6).

7. **Conversational chat layer** (`draft-chat.service`, `/chat`) — greeting/intent
   routing, natural replies, "ready to draft" hand-off. Pure UX; engine is
   headless. → **Stays in TS**, calls the pipeline on ready-to-draft.

8. **Graceful degradation when the provider is off** — the TS pipeline returns a
   manual-entry shell with advisories rather than failing. → **Stays in TS.** Note
   the engine *improves* the keyless path: even with no LLM, `/v1/draft` can render
   a document with every narrative slot as `[to be drafted]` (that's the engine's
   normal no-LLM mode), so "AI off" still yields a real, structured, refusal-checked
   skeleton — better than today's empty shell.

**Net:** the engine takes over sections-decision-for-procedural-framework,
refusals, computations, structure, VERIFY markers, and sign-off. TS keeps triage,
offence-KB retrieval, prose-audit, streaming, tenancy/quota, case context, chat,
and degradation. Nothing useful is lost.

## 8. What must be built in the ENGINE before the API can be honest

The routing is only worth doing if the engine exposes a clean contract. Prereqs, in
the engine repo:

1. **Refusal codes.** Give every refusal a stable `code` + `severity` +
   `fields_implicated`. Today they're bare `reason` strings. This is the contract
   §4 depends on. (Touches every pipeline's `_refuse(...)` call and the rules
   modules; the generated refusal catalogue in `tools/refusal_report.py` becomes
   the source of truth for the code list.)
2. **Per-pipeline field adapters** — the flat-`fields`-JSON → typed-kwargs mapping,
   one per pipeline, each tested against its `build()`. This is where ISO-date and
   enum coercion lives, and where a bad value becomes a 422.
3. **`/v1/doc-types` introspection** — emit the field/slot contract per pipeline.
   Some of this exists implicitly (averment registry names docs; pipeline modules
   name templates); it needs consolidating into one machine-readable descriptor.
4. **Fact-sheet construction from a case record** — a documented mapping from the
   TS case-record shape to `MatterFactSheet.create/revise`, so `matter_id`/`version`
   have a real source.
5. **The FastAPI app itself** — `service/`, Pydantic models mirroring §3–§4,
   threadpool-wrapped engine calls, the shared-token auth, OpenAPI out.

None of these change the engine's core logic — they wrap and expose it.

## 9. Migration order — never a half-routed frontend

The danger is a state where the framework is engine-decided but the refusals aren't
(or vice versa): the UI looks connected but silently bypasses half the guarantees.
To avoid that, migrate **one document type end-to-end at a time**, behind a flag,
with the whole pipeline (route + refuse + render + sign-off) on or off together.

**Phase 0 — engine prereqs (§8).** Refusal codes, adapters, `/doc-types`, fact-sheet
mapping, FastAPI app. No frontend change yet. Ship the service, tested in isolation,
callable from a script. *Exit:* `/v1/draft/s138_notice` produces a rendered doc and
a structured refusal for a bad input, proven by the engine's own tests.

**Phase 1 — one document, shadow mode.** Pick **s.138 notice** (fully rule-driven,
no narrative slots, so no model-in-the-loop to muddy the comparison; and it already
has the richest refusal set). The Node `/pipeline` route, for this doc type only,
*also* calls `/v1/draft` and logs a structured diff between the engine's result and
the current TS output. **Nothing user-visible changes.** *Exit:* the diff is
understood — every place the engine refuses/decides differently from the model is
explained and is an engine win.

**Phase 2 — one document, live behind a flag.** Flip s.138 notice to render from the
engine for firms with the flag on. The model's role for this doc: none (no slots).
The refusal path renders as a conversational message. Sign-off writes to the engine
audit. *Exit:* the flagged cohort drafts s.138 notices entirely through the engine,
refusals-and-all, with no regressions.

**Phase 3 — add the slot-bearing documents, one at a time.** Regular bail → plaint →
writ → MACT → the rest. Each brings the model back in for slots only (§5.3) and the
TS VERIFY audit on the slot prose (§7.2). Each migrates fully (route+refuse+render+
sign-off) before the next starts. Order by refusal-richness (most guarantees first).
*Exit per doc:* that doc type is engine-routed for the flagged cohort.

**Phase 4 — delete the divergent TS logic (§10) and remove the flag.** Once every
doc type is engine-routed and stable, the CLASSIFY-decides-framework path and
`old-to-new-law.ts` are dead code. Remove them; make engine routing the only path.

At no point is a single document type "framework-routed but refusal-bypassed": each
type is either fully old or fully new. The flag is per-doc-type, not per-feature.

## 10. CLASSIFY and old-to-new-law.ts — I agree: delete, don't fallback

You're right, and here's the reasoning made explicit:

- **`old-to-new-law.ts` → delete** (Phase 4). It is a hand-maintained flat map that
  (a) duplicates `section_mappings` + `dual_code_router` with *no date/provenance
  logic*, and (b) will drift the moment either side is edited. A second, less
  correct answer to "what's the section" is a liability: when they disagree, which
  does the advocate trust? Keeping it as a "fallback" institutionalises the
  divergence. Its one genuinely useful behaviour — *spotting a repealed citation in
  the advocate's brief text* — is subsumed: the brief goes through extraction into
  engine fields, and the engine cites the correct section, so a stale citation in
  the brief simply doesn't survive into the draft. If we want the proactive "you
  wrote 439 CrPC" hint kept, it belongs as a thin lookup over the engine's
  `section_mappings` table (one source), not a parallel map.

- **CLASSIFY's framework role → delete; CLASSIFY's offence-KB role → keep** (this is
  the nuance). CLASSIFY does *two* things fused together: it picks *procedural
  framework* sections (which the router now owns — delete) **and** it retrieves
  *substantive offence* sections from the KB (which the engine does not do — keep,
  §7.1). So it's not "delete CLASSIFY," it's "**stop letting the model decide the
  framework; keep the offence-KB retrieval**." After Phase 4, CLASSIFY becomes
  offence-KB-retrieval-only, feeding `fields`, and never states a procedural section
  the router should own.

If you want the harder line — port the offence-KB into the engine as a VERIFY table
and delete CLASSIFY entirely — that's defensible, but it's a bigger port and the KB
is genuinely orthogonal to the router, so I'd sequence it *after* routing is proven,
not as a blocker.

## 11. Open questions for you

1. **Deployment topology** — same host/container as the Node API (localhost call),
   or a separate service? Affects the auth/network model in §2.
2. **Offence-KB** — keep in TS (my rec) or port into the engine as a VERIFY table?
   (§7.1, §10). Not a blocker either way; changes Phase 4's scope.
3. **docx assembly** — the engine returns a rendered `.docx`. The TS editor today
   works on structured blocks/prose it can stream into an editable surface. Do we
   want the engine to *also* return the document as structured blocks (so the
   existing editor keeps working), or does the editor move to "render → download,"
   losing inline editing of engine-produced sections? This is the biggest UX fork
   and worth deciding before Phase 2.
4. **Which doc type leads Phase 1** — I propose s.138 notice (no slots, richest
   refusals). Agree, or lead with a slot-bearing one to prove the model handoff
   earlier?
